# ADR 0004: The editor is a native dcimgui widget, not a ported node library

Status: Accepted
Date: 2026-08-18

## Context

The project needs a blueprint canvas: nodes placed and dragged, pins wired with bezier links, pan and zoom, rectangle selection, context menus, a node search popup, and cut, copy, paste, undo, redo. Two C++ libraries do this well, imnodes and thedmd/imgui-node-editor, and neither has a C binding.

Both routes were built and then removed. A full C23 port of imgui-node-editor existed in the tree, and so did a C++ imnodes spike behind a hand-rolled C ABI shim. Both were deleted for the same reason: they duplicated the editor interaction model. Each library owns its own notion of what a node is, where it sits, which pin is being dragged, and what is selected, and this project already owns all of that in `struct graph` and `struct node` (core/graph.h, core/node.h), with `node.x` and `node.y` as the layout hint and graph JSON as the persistence and undo format. Running a second model means mirroring every interaction across the boundary, and every disagreement between the two is a bug that appears only at the seam.

The host layer is settled and already pure C. cute_framework provides `cf_app_init_imgui()`, and dcimgui.h is the C binding for ImGui generated by dear_bindings, the same generator cimgui uses, so the ImGui C API is available directly.

## Decision

The editor is an app-specific C23 widget in editor/editor.c, written directly against dcimgui. It owns the blueprint interaction loop: node and pin rendering, links, dragging, pan and zoom, selection, context menus, node search, and graph-JSON undo, redo, clipboard, and persistence. The public surface stays small: `editor_new()`, `editor_free()`, `editor_draw()`, `editor_spawn()`, `editor_save()`, and `editor_load()` in editor/editor.h.

The widget does not preserve imnodes or imgui-node-editor API compatibility, and neither library is a dependency. Runtime evaluation stays out of the rendering code in editor/eval_view.c. The graph, evaluation, and serialization layers stay hand-written C23 and free of any ImGui or cute_framework include, per `SCOPE-1` in docs/spec.md.

## Consequences

There is one model of the graph. Selection, layout, and link state read and write `struct graph` directly, so there is no mirroring step and no divergence to debug. Adding a blueprint-specific interaction, exec pin ordering with `graph_connect_exec()`, per-pin type coloring driven by `pin_spec.type`, split struct pins, or a debugger's current-node highlight, is a change to editor/editor.c rather than a fight with a library that does not know those concepts exist.

The build stays entirely C: no C++ translation unit, no ABI shim, no second ImGui binding.

The cost is that every canvas feature is hand-written. imgui-node-editor's link routing, hover highlighting, and navigation smoothing are not free here. The first native version skips a minimap, INI-based layout persistence, and multiple editor contexts; docs/roadmap.md schedules them. editor/editor.c also becomes the largest file in the project, holding widget state, coordinate transforms, layout, interaction, rendering, and the graph bridge.

## Alternatives rejected

### Port imgui-node-editor to C23

This was built and removed. The port is large, and it brings its own editor context, node and pin registry, selection and layout state, and persistence format, all restating what core/graph.h holds. Maintaining it means tracking upstream C++ changes by hand in translated C forever, and every blueprint feature has to be threaded through a model designed for a general node editor rather than for exec pins, ordered fan-out, and typed data pins.

### Wrap C++ imnodes behind a hand-rolled C ABI

This was built and removed too. The shim reintroduces C++ into the build and adds a boundary every interaction crosses twice, once to push graph state into imnodes and once to pull user intent back out. imnodes also has no concept of execution pins, link ordering, or pin type compatibility, so `pin_types_compatible()` and `graph_connect_exec()` would be enforced outside the widget the user touches, which is where a validation rule is least useful.
