# Laya Retrieval and Decision Design

Checked 2026-09-23 against upstream `NandhaKishorM/laya`, the exact fork commit pinned by this worktree, and the local command-palette experiments.

## Finding

Retrieval and Laya solve different parts of the task. Search should find a small set of valid edits; Laya should choose among those edits. An editor graph is useful for enforcing facts such as which prototype an instance inherits from and which properties an asset supports. Those constraints should narrow the candidate set before semantic ranking.

The earlier [speed and decision note](laya-gpt-oss-speed-options.md) mentions retrieval without identifying its local evidence. The archived `space-cadet-palette` worktree does contain a reproducible ColBERT-small versus lexical matrix for finite UI actions. It is a retrieval result, not evidence for ColBERTv2 or property edits. The hierarchy code in [`tools/mcp/laya.mjs`](../../tools/mcp/laya.mjs) is a bounded caller-driven tree; its checked-in tests mock Laya responses.

## Local evaluations

The archived 36-request finite-action corpus had 22 supported actions and 14 deferrals. At one retrieved candidate, lexical search retained the intended action for 19/22 supported requests and the 33M-parameter `answerai-colbert-small-v1` retained it for 21/22. At five candidates and the tested 0.8 gate, lexical plus Laya accepted 10 correct and 2 wrong actions; ColBERT plus Laya accepted 14 correct and 0 wrong. Those thresholds were explored on the same corpus, not validated on a holdout. The ColBERT path had 0.456 s p50 and 0.713 s p95 end-to-end latency, versus 0.436 s and 0.557 s for lexical. The archived branch `cwaldner/space-cadet-palette` contains `tools/editor-command/compare_retrieval.py` and `tools/editor-command/evals/tuning-results.json`; this branch does not depend on them.

We then ran the pinned local Laya service on [48 new property-selection cases](../../tools/mcp/evaluation/laya-property-cases.json): 36 supported single edits across two prototypes and three fields, plus 12 requests that should defer. The [headless runner](../../tools/mcp/evaluation/compare-laya-choices.mjs) offers the same six complete edits to flat and tree variants, reverses option order, and measures the current 0.8 acceptance gate. It excludes retrieval and value construction, so its accuracy is for choosing the edit only. Each row below is one ordering of the same 48 requests. `Raw` counts correct top choices among 36 supported requests, before the confidence gate.

| Question design | Raw, forward | Raw, reverse | Accepted correct at 0.8 | Calls per request | p50/p95, forward |
| --- | ---: | ---: | ---: | ---: | ---: |
| Flat six edits plus defer | 18/36 | 22/36 | 0 | 1 | 385/472 ms |
| Two-stage prototype then field | 13/36 | 16/36 | 0 | 2 | 646/798 ms |
| Known prototype, four verbose field choices | 24/36 | 28/36 | 0 | 0-1 | 329/392 ms |
| Known prototype, four compact field choices | 25/36 | 33/36 | 0 | 0-1 | 279/352 ms |
| Known prototype, three compact fields without defer | 27/36 | 27/36 | 0 | 0-1 | 272/325 ms |
| Known prototype, three batched `noul` questions | 7/36 | 7/36 | 1 | 0-1 | 525/640 ms |

The known-prototype variants are favorable upper bounds: the runner resolves `Player`/`Ship` and `Enemy`/`Foe` from the wording before calling Laya, and locally defers requests with no unique named target. Their unsupported-request score is partly due to that deterministic filter. In the flat and tree variants, unsupported requests frequently received a non-defer raw proposal. All variants deferred all 12 unsupported requests at 0.8 only because the gate also rejected nearly every supported choice. Lowering the gate to 0.1 for the flat variant accepted 26 correct and 15 wrong proposals across both orderings; a post-hoc 0.2 gate on the known-prototype verbose variant accepted 14 correct and 0 wrong across both orderings, but that cutoff has no independent validation and covers only 14/72 supported trials. The large order effects and low coverage make a threshold change unjustified.

To repeat the comparison against a running local service, set `LAYA_API_KEY_FILE` to its key file and run `node tools/mcp/evaluation/compare-laya-choices.mjs` from the worktree root. Set `LAYA_EVAL_MODES=scoped,scoped_compact,scoped_no_defer,scoped_noul` for the focused variants and `LAYA_EVAL_OUTPUT=.chibi/laya-results.json` to retain per-case results. These are live-model evaluations; the editor is not opened or changed. The measured service identified itself as `laya-rl-agent`, base English weights, ModernBERT-large on CPU, with a 512-token context and 192-token question-head budget.

The separate [prior direct-checkpoint comparison](laya-gpt-oss-speed-options.md) found that the typed-decisions checkpoint accepted none of 18 held-out choices at its tested gate, despite getting 18 raw choices correct. The current service uses the base English checkpoint. Its running container's original image layers are no longer available to start an isolated second service, so this new 48-case run does not compare checkpoints. The earlier direct result is useful context, not a paired result for this fixture.

This gives a clear answer for the current menu: a depth-first or two-stage tree does not improve selection, and adding ColBERTv2 cannot repair decisions when all six correct candidates are already present. Compact questions help raw selection when the prototype is known, but still do not produce accepted edits at the current gate. The missing capability is reliable intent-to-edit matching and calibrated abstention for this editor domain.

## What upstream Laya supports now

At the time of this check, upstream `main` was commit [`010bacef`](https://github.com/NandhaKishorM/laya/commit/010bacef009c855ccba814b51f7c8e1d38ab5e3f). It has an optional `predict_shortlist(agent, state, questions, embed_fn, k)` helper. It embeds the serialized state plus question instruction and each choice option, ranks options by cosine similarity, retains the top `k`, and calls Laya once on the reduced choice. `embed_fn_from_agent()` reuses the already-loaded encoder by mean-pooling token vectors. The upstream implementation explicitly notes that a dedicated bi-encoder will usually shortlist better. This helper is retrieval by caller-supplied embeddings; it does not make the decision head score every original option, and the returned probabilities are conditional on the retained shortlist. If the correct action is omitted, Laya cannot select it. [Upstream shortlist implementation](https://github.com/NandhaKishorM/laya/blob/main/laya/shortlist.py) · [Upstream README](https://github.com/NandhaKishorM/laya#honest-limits)

The README's question format is a state plus named typed questions. A `choice` question has a direct `instructions` string and a `criteria` map from a short key to text describing its meaning. It documents caller-created coarse-to-fine questions for large option sets; it does not provide an editor decision tree or a depth-first search planner. The README describes 512-token context and a 192-token option/question-head budget for the English checkpoint. [Question examples and option-budget discussion](https://github.com/NandhaKishorM/laya#quickstart-route-mode) · [Shortlist source](https://github.com/NandhaKishorM/laya/blob/main/laya/shortlist.py)

ColBERTv2 is a more expressive retriever: it represents each query and candidate with token vectors and scores their token-level matches, then uses a compressed index. That can help when one pooled vector misses a specific phrase or property. It adds a separate model, candidate index, and retrieval path. Its reported information-retrieval results are not editor-command accuracy results. [ColBERTv2 paper](https://arxiv.org/html/2112.01488v3)

## What our pinned service supports

The Docker image pins [`sirgio03/laya` commit `e683ef8d…`](../../tools/laya-jev/Dockerfile), whose package reports version 0.3.3. Its source tree has no `laya/shortlist.py`, and [`laya.__init__`](https://github.com/sirgio03/laya/blob/e683ef8d37b0828758a4e9e2004d1ab7fc3505bc/laya/__init__.py) does not export `predict_shortlist` or `embed_fn_from_agent`. Therefore, the upstream helper is not available through our pinned package. The pinned `Agent` does expose its tokenizer and encoder, so an adapter could implement the same mean-pooled embedding shortlist without changing model weights. Our service already loads the model once and preflights token budgets; it checks each option's token length and the combined model head/state budget, and caps independent questions at six. [`Agent` at the pinned commit](https://github.com/sirgio03/laya/blob/e683ef8d37b0828758a4e9e2004d1ab7fc3505bc/laya/agent.py) · [local service](../../tools/laya-jev/server.py) · [token-budget checks](../../tools/laya-jev/token_budget.py)

The separate checkpoint downloader pins English weights revision `1c5edc17…` with a 512-token context and `head_max_len = 192`. The checkpoint includes temperature values by question type and option-count bucket. That is useful calibration support, but it does not establish that the current 0.8 decision threshold is calibrated for our editor commands. Calibration needs held-out palette examples and must be measured at the actual option counts. [Pinned checkpoint configuration](https://huggingface.co/convaiinnovations/laya/blob/1c5edc17a7acd8701df6fc341c0d179f1c62c982/rl_agent_config.json) · [model downloader](../../tools/laya-jev/download_model.py)

## Improvement plan

1. Keep the C fast path for a structurally unique, direct property edit. The first safety change in this branch makes it defer requests with conditional or compound wording before a one-option menu can bypass Laya. Test this through the headless native command path.
2. Record real editor catalogs and expected complete edit operations, including the selected scene, inherited prototype, property value, and unsupported requests. Hold out entire intents and scenes. Measure how often the current C candidate generator includes the correct edit before asking Laya. The synthetic six-action fixture above isolates the choice head, not candidate generation or execution.
3. If candidate recall is the bottleneck, compare a compact lexical shortlist with the pinned encoder's embeddings at the same `k` and catalog revision. Keep graph relationships and legal property/value constraints in C. A semantic shortlist may rank legal edits; it must never invent one. Add ColBERTv2 only if this simpler shortlist fails a held-out recall target and its measured end-to-end gain covers the extra model/index cost.
4. If the correct action is present, measure Laya choice and abstention on a held-out suite before changing its prompt or confidence gate. A reasonable go/no-go target for the one-edit path is at least 90% accepted correct commands, zero wrong automatic edits in at least 100 varied unsupported or misleading requests, and warm end-to-end p95 below 500 ms in both option orders. Test the typed-decisions checkpoint on that identical suite if an isolated service is available. Do not extrapolate from the prior 24-case direct run.
5. Do not add DFS or a default two-call decision tree. Reconsider grouping only for a catalog too large to fit within the model's option budget, and count the full latency and branch errors. If one-call Laya cannot meet the held-out safety and coverage target, keep it as an experimental bounded chooser on this branch and use the general editor agent for open-ended commands.

Report candidate Recall@K, conditional Laya accuracy, accepted-wrong rate, coverage/clarification rate, and end-to-end latency separately. The retrieval result must not be counted as a Laya decision win, and upstream benchmark gains must not be treated as evidence for this editor domain.
