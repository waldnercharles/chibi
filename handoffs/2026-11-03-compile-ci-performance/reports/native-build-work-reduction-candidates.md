# Native-build work reduction candidates

The measured diagnostic run took 122.42 s wall, with 320.03 s summed child wall. Those are different quantities. The independent canonical run recorded 141.38 s wall with different ambient contention; the diagnostic result is not a before/after speedup. Worker harness preparation totals 0.338 s, plus 0.013 s in the parent. That phase is preparation of the BuildTests program, not all fixture setup or child compilation. Fixture work remains inside execute.

The monotonic trace shows foreign samples running from 60.672 to 122.271 s, workloads from 61.080 to 99.571 s, and the last other case finishing at 86.350 s. These case spans overlap. `native-build-observed-critical-path.json` retains every span. Removing workload work alone predicts zero direct wall saving on this observed dispatch graph; resource contention effects still need measurement. Reducing only foreign-sample duration can directly save at most 22.700 s before workloads become the critical path. For example, a hypothetical 20% foreign-case reduction would save 12.320 s on this fixed graph, while a 20% workload reduction alone saves runner work but no direct wall time. These are schedule calculations, not measured intervention results.

The suite already builds/reuses one recovered compiler and one cached emitter across workers. LinksAProgramAndReusesIt verifies the emitter cache identities do not change when a separate fixture folder builds. Suite.cache is shared. The native_aot driver only compiles its emitter when the keyed file is absent. Adding another compiler cache or runner would duplicate existing behavior.

Foreign samples contain different assertions and compilation inputs. No duplicate whole sample build has been identified. Combining them into one executable would change compilation inventory and package/foreign-library interactions; it needs an explicit equivalence review and is not proposed here.

A narrower workload hypothesis removes four repeated source-to-IR operations. In native_aot.Driver.Native, optimization mode affects the output identity and downstream Run; CollectScalar and emitter requests do not receive it. Therefore each O0/O2 pair repeats the same frontend inputs. The retained source.ll is written before opt and llc in Driver.Run. The proposed experiment would compare each pair's source.ll bytes first, then build O0 through the unchanged CLI and pass that exact retained IR to the O2 driver, retaining eight program executions and all checksum assertions. AddsLineTablesWithG already reads retained O0 source.ll; RunsWithLLVMAndNoCCompiler proves actual O2 CLI dispatch, while LinksAProgramAndReusesIt proves its separate key.

This would explicitly reduce workload-specific O2 CLI invocations from four to zero. Other cases prove O2 option handling, but that is a change to the named workload path inventory, not implicit equivalence. Existing DriverBuild also hardcodes static linkage while these workloads use dynamic linkage, so it cannot be reused unchanged. A test-local entry could call the existing public driver.Run with dynamic linkage, but the integration/setup cost and the lost workload CLI path need independent approval. Workload reuse remains pending, with no source edit or performance claim.

The meaningful reused-IR negative control is valid IR returning a wrong checksum, linked at O2 through the same dynamic path. Each unchanged README checksum assertion must reject it. A malformed or missing IR output must fail rather than use an old binary. This control is independent of implementation shape. Before changing the harness, collect one narrow phase sample per kernel/mode and at least three paired canonical case runs with the same cache state and pinned toolchain. Prediction for summed frontend work is bounded by four of eight frontend operations removed; seconds saved are still unknown. The observed critical-path prediction remains zero direct suite wall saving from workload reuse alone.

A second experiment can compare the already-built native candidate with the installed CLI on exactly these same eleven foreign projects and four workload sources, preserving sample source bytes, working directories, argument arrays, vendor/font staging, assertions, both workload modes and deadlines. Only these assertion-only cases would use the candidate; recovery, invalidation, failed-output and cancellation cases keep their original CLI path. The native driver accepts explicit --compiler, --core, --root, --entry Main, --target, --level and --llvm flags, prints the same program marker, retains source.ll, and records library-sha256 in its receipt. Its macOS linker lookup also requires ld64.lld, while the legacy cases currently stage only ld.lld; both aliases must resolve to the same pinned lld binary in the comparison. Use the root cache mode rather than --source/--output so the vendor receipt assertion remains present.

That comparison is measurement-only. Replacing the installed CLI in named cases would remove eleven foreign plus eight workload CLI invocations, so it requires explicit review rather than silently claiming the old path inventory remains. Existing native subset gaps mean a faster local test number is insufficient. The candidate must first pass every same-named assertion and diagnostics control on both platforms. No such comparison or replacement has been run in this lane.

The confirmed bundle-manifest race is a separate correctness correction needed to preserve target inventory. Its external patch and real-producer forced-overlap regression are under native-bundle-fix. It does not supply a compile-speed result.
