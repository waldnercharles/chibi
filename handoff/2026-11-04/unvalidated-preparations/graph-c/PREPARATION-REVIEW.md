# Source preparation review

## Brief and estimate

Transform: fixed admitted source/tool identities, live process observations and exact wait evidence into one bounded graph-c ownership result. Consumers are the independent reviewer, fixed controller and its terminal verifier. This is cold proof code, not a general supervisor or product process API.

The fresh source has 5,620 entries, including 4,087 files totaling 50,372,361 bytes. Each full input fence traverses the fresh and preserved-original source once. The inherited tool manifests describe 147 tool paths totaling 454,783,051 bytes, 104 Graph tool paths totaling 395,735,009 bytes, 4,090 C-root entries totaling 158,844,304 file bytes, and 1,282 Python entries totaling 26,315,136 bytes. Some alias paths intentionally describe the same underlying bytes; each exact path/identity remains fenced. These manifest totals alone approach 1.136GB per full fence including both source copies, before small metadata, supplemental proofs and directory checks. Two full fences are required to detect execution-time mutation. One redundant fresh-source post-scan was removed by returning generated facts from the existing fence.

Hashing cached bytes at an illustrative 0.5–2GB/s would take about 0.6–2.3 seconds per fence before file-open/stat/parsing work. That bandwidth and actual latency are unknown here, not measured claims. Uncached I/O and thousands of filesystem operations may dominate. Every fence shares the original clocks; a slow fence fails rather than obtaining another window.

The unchanged passive observer is bounded by 256 visible process rows, 64 retained identities, 16 eligible identities and depth4. This executor's earlier source-only evidence lacks the narrow task/children interface; the accepted design uses bounded global /proc discovery only, never as attribution or signal authority. At an illustrative 12 visible processes, twenty nominal observations during20ms require roughly1,200 scan file operations before ancestry checks. Scheduling and observation latency are unknown. One1ms poll preference is not a guarantee of twenty opportunities. A missed registration irreversibly fails the attempt. No source sleep, process stop or timing change is introduced.

## Structure and lifetime

One fixed controller invokes the unchanged outer owner, one fixed worker, one dedicated inner owner and the exact retained graph-c ELF. No arbitrary payload or general command mode is added. The inherited broad fences account for much of guard.py; removing them would weaken existing evidence. Parent identity, child pidfd ownership, terminal output, exact waits, ECHILD and actual exits remain distinct evidence, not interchangeable counters.

The only successor-core delta is documented in CORE-DELTA.md. The original core and completed proofs remain unchanged. A partially initialized core remains reachable; failures at the pre-exec gate cannot leave untracked graph-c descendants. Cancellation remains latched through receipt/close work. Invalid poll events now fail rather than treating an errored descriptor as retired.

## Correctness and verification limits

- No syntax/compiler/import/native/control/controller/owner execution was performed. All executable sources require independent source and execution admission; none is called tested or passed.
- Exact GNU diagnostic candidates still need independent source/tool validation. Literal strings support vocabulary only; unknown output is retained as failure.
- The actual20ms control cannot honestly count the uninstrumented shell's internal forks independently. Reports must distinguish known root/shell launches, observed registrations, rejected unknown adoptions and final kernel ECHILD.
- The original125-second interval includes the final five-second unchanged-outer cleanup reserve. Final external observation of actual controller exit is still required; writing a provisional success receipt does not establish it.

## What I would delete

No production source or old proof was replaced. Keep prior immutable evidence. Do not add another owner loop, generic launch mode, permissive output matcher or per-poll hashing. The duplicate post-source inventory has already been removed.

## What I would measure

After separate admission: complete input-fence duration, passive discovery overhead and missed-registration behavior, actual terminal timings, native20ms topology visibility and exact stderr bytes. These measurements must not extend graph-c's original window or turn an unknown outcome into success.

## What I would leave alone

The authored CTests assertions/timing and generic outer owner stay exact. The bounded dictionaries and plain process state machine are adequate at64 identities. Existing closure fences and path-specific metadata remain explicit despite code volume, because their consumer is exact independent admission, not a reusable API.
