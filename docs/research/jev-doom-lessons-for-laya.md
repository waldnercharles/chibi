# Jev Ultrafast and DOOM MultiVec: lessons for Laya

Reviewed the repositories' current README, implementation, and documentation on 2026-09-23.

## Jev Ultrafast

[Jev Ultrafast](https://github.com/browser-use/jev-ultrafast) is a Python browser-control agent using TypeSafe Jev for discrete decisions and an optional small language model for text entry. It is not a general conversational computer-use plugin. The goal stays fixed while the agent repeatedly observes the page, asks for the next operation and target, executes one action, then observes again. Its README describes operations and a fresh indexed table of visible elements; [`model.py`](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/model.py) supplies role, label, current value, and per-operation target choices, alongside short natural-language operation descriptions. [`questions.py`](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/questions.py) adds explicit policy instructions about satisfying all requirements, using current values and action history, not repeating satisfied steps, and requiring visible evidence before DONE.

This is multi-turn control in the sense of a repeated observe-decide-act loop, not a free-form chat thread or a planner that rewrites the goal. The choice request includes the original goal, current structured page state, and up to ten recent actions. After action execution, the new page observation and whether it changed are recorded for the next choice. The browser rejects stale or obscured targets before input; a stale decision is discarded and recomputed. Runs have a step budget and stop after three consecutive non-WAIT actions that leave the page unchanged. A small text model is called only when a selected action needs a value, and that helper also receives the goal, field label/value, page context, and recent actions. See [`agent.py`](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/agent.py), [`snapshot.js`](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/snapshot.js), and the [README](https://github.com/browser-use/jev-ultrafast/blob/main/README.md).

### Transfer to the editor palette

- Carry the user's request unchanged through a sequence of typed editor operations. After each operation, re-read authoritative editor state and give the next decision the original request, current state, and compact action history.
- Give each candidate a short, distinguishing description: target identity and scope (for example, `Player prototype (used by Ship)`), property meaning (`visible sprite width` versus `collision hitbox shape`), current value, and valid operation. Descriptions should be generated from editor metadata, not guessed from user wording.
- Keep operation and target choices constrained to operations the C executor can validate. Treat each proposal as provisional until the live editor revision and target still match; reject and re-decide on stale state.
- Track whether an action changed the relevant editor state. Bound repeated no-op attempts and require a fresh readback for completion. A model's DONE/accepted choice is not proof of a successful edit.
- The repository provides a tested interaction pattern, not evidence that adding more prose alone makes Laya accurate. Compare description variants and history policies on held-out palette requests before adopting them.

## SauerkrautLM-Doom-MultiVec

[SauerkrautLM-Doom-MultiVec](https://github.com/VAGOsolutions/SauerkrautLM-Doom-MultiVec) is a small supervised DOOM controller, not an embedding search system or language-conditioned action chooser. The README calls it a ModernBERT encoder with hash and depth embeddings, per-token representations, attention pooling, and a fixed action-classification head. Its [inference guide](https://github.com/VAGOsolutions/SauerkrautLM-Doom-MultiVec/blob/main/docs/guide/inference.md) explicitly says inference is a single classifier forward pass with softmax over the fixed action set; it does not use query embeddings or MaxSim retrieval. The model receives a 40×25 ASCII frame and depth data, then predicts among four game controls. The visual play loop repeatedly feeds each new frame to that classifier, and may combine compatible top actions with a hand-written probability rule ([`play_doom_visual.py`](https://github.com/VAGOsolutions/SauerkrautLM-Doom-MultiVec/blob/main/scripts/play_doom_visual.py)). It has no natural-language goal, action descriptions, editor candidates, or conversational memory. Its training guide reports 31K human gameplay frames with action scores ([data pipeline](https://github.com/VAGOsolutions/SauerkrautLM-Doom-MultiVec/blob/main/docs/guide/data-pipeline.md)).

The useful idea is domain-specific supervision: a small, fast policy can work when observations and outputs are stable, and a substantial labeled demonstration set is available. For the palette, that could eventually motivate a small router/ranker trained on reviewed command traces and structured editor state. It would be a separate experiment requiring held-out semantic edit coverage and abstention tests. The DOOM checkpoint or its multi-vector architecture does not transfer directly: editor requests are open-ended, candidate properties vary by project, and acting on the wrong object/property is materially worse than choosing a slightly suboptimal game control. Keep the C executor as the authority for valid operations and scope.

## Conclusion

The strongest directly reusable pattern is Jev's context shape and control loop: descriptive typed candidates, current observation plus short recent history, one bounded action at a time, revision/freshness checks, and post-action readback. “Multi-turn” should mean that supervised loop; it need not add a chat transcript or another model call per edit. Doom MultiVec supports the possibility of a future editor-specific trained selector only if we first build a broad, reviewed trace corpus. Neither upstream project establishes that an Laya prompt rewrite or a hierarchy will make the present palette accurate; that needs a paired held-out evaluation.
